# BharatSource frontend design guide

Reference for redesigning future pages (Directory, Recruitment, Consultations…) so the whole suite reads as one product. This documents what the homepage/navbar redesign (`frontend/app/page.tsx`, `components/Navbar.tsx`, Aug 2026, **v5.4**) actually implemented — not aspirational rules. When code and this guide disagree, trust the code.

It sits on top of, not instead of, `CLAUDE.md` §2/§6 — no emoji, native `<select>` for filters, zero horizontal overflow at 390px, **local images only, never hot-linked**.

**Scope note**: the color palette and `.container-bs` width are **site-wide changes** (CSS custom properties / a shared class in `:root`/`globals.css`). The **layout/content patterns** (module row, stats strip, how-it-works, advertise section, feedback section, the Reveal motion system, the auth-aware/context-aware Navbar behavior) apply to the homepage, `/about` and the Navbar itself; Directory, Recruitment and Consultations still use their pre-existing page layouts (though they already inherit the shared Navbar behavior) and are the next redesign targets.

## Version history (why some earlier guidance was replaced)

- **v1**: bento layout with an activity-feed sidebar.
- **v2**: navy/orange palette — too close to the old blue/orange to read as a real change at UI scale.
- **v3**: blue/orange/green palette (kept), bento layout (Bharat Agent large + Directory/Recruitment stacked beside it), advertise + feedback sections added.
- **v4**: the bento layout was replaced with **three equal-weight module tiles in one row** — product direction was explicit that the asymmetric bento "wasn't looking well" and should become three-in-a-line. Also: hero/closing CTAs became auth-aware, the hero's "BharatSource" badge pill was removed, the Navbar gained a suite-scoped Products menu (Directory + Recruitment only) plus Blog/About us, the language toggle was removed from the Navbar, and the user-menu became context-aware (minimal profile+logout on suite pages, full Dashboard/Listings/Inbox on Directory pages).
- **v5 (current)**: v4's three-equal-tiles row was replaced by a **single unified "hero card"** (`AgentHeroCard.tsx`) on explicit product-owner request, loosely modelled on a familiar SaaS-homepage AI-agent panel layout — Bharat Agent is the card's dominant half (icon/badge/heading/copy + a static "ask bar" + two routing-chip examples as the signature visual), with Directory and Recruitment nested as two compact linked tiles in a lighter zone at the card's bottom, inside the *same* card boundary rather than as siblings. This is a deliberate, explicitly-requested reversal of v4's "equal-weight, no dominant panel" rule — see Brand principle below, updated accordingly. Also fixed: the Navbar's suite-scoped `Products` trigger (`SuiteProductsMenu`) now uses the exact same typography as the plain `Blog`/`About us` links (no bold weight override, no leading icon) so it reads as one consistent nav row instead of a visually heavier button. `ModuleCard.tsx` and `.home-modules-row` are kept as reference (like `BharatAgentPanel.tsx`/`ActivityFeed.tsx`) — don't resurrect the three-equal-tiles row without a new explicit request.
- **v5.1**: on explicit request, the intro hero + `AgentHeroCard` (with Directory/Recruitment visible) were compacted to fit above the fold with **zero scrolling on common desktop viewports** (verified 1280×720 up to 1920×1080, ~600px of vertical budget from the top of the header to the bottom of the nested product tiles). This is a deliberate, page-specific exception to the general **Page H1** type-scale row in Typography (`clamp(32px, 5vw, 54px)`) — the homepage H1 now runs `clamp(24px, 3vw, 36px)`. Section-1/section-2 padding, the card's internal padding, and its type sizes were all tightened correspondingly — see the actual `clamp()` values in `app/page.tsx`, `AgentHeroCard.tsx` and the `.agent-hero-*` rules in `globals.css` rather than re-deriving them. If a future homepage section needs to reclaim this vertical budget (e.g. a new module joins the row), re-check the fold with the same viewport set before shipping — don't just eyeball one browser window size.
- **v5.2**: two follow-up fixes, both on explicit request. (1) The H1's v5.1 forced `<br />` after "needs," read badly once tried — removed in favor of tuning `maxWidth` (760→**600**) so the natural wrap breaks after "business" instead of orphaning "place" alone; prefer this approach (adjust `maxWidth`, check the render) over a hard break if the H1 ever needs re-tuning again. (2) `AgentHeroCard`'s Directory/Recruitment moved from a full-width strip *below* Bharat Agent to a **compact vertical column to its right** (`.agent-hero-side`, stacked `.agent-hero-product` tiles, ~220–260px wide) — closer to a common SaaS pattern of pairing a main AI-agent feature with a narrow app-list beside it, and it reads as less "stretched" than the old full-width strip. `.agent-hero-card` also gained `max-width: 1040px; margin: 0 auto` — at full container width the two-column content (~680px) was leaving very wide, un-intentional-looking margins; capping the card itself (rather than widening its content to fill the container) keeps it feeling deliberate. A short two-tone accent rule was also added between the hero card and the stats strip as a section break — **reverted in v5.3, see below**, don't re-add it without a new request.
- **v5.3**: three more explicitly-requested fixes. (1) Removed the intro section's `borderBottom: "1px solid var(--border)"` — it read as a stray line sitting between the H1 and the hero card. (2) Removed the v5.2 accent-rule section-break entirely (see above) — the product owner tried it and asked for it back out; if a section break between the hero card and stats strip is wanted again, get a fresh explicit direction rather than reintroducing the same gradient rule. (3) **`AgentHeroCard`'s Bharat Agent half stopped mocking a search bar.** The v5.1/v5.2 "ask bar + routing chips" (`.agent-ask-bar`, `.agent-chip`) looked like an actual, clickable search input — confusing, since Bharat Agent has no live destination and nothing there was functional. It's gone. `.agent-hero-main` (the Bharat Agent half) is now styled as its own `card card-flat` — the **same visual language as the Directory/Recruitment tiles beside it** (icon tile, badge, heading, one-line description, a status line pinned to the bottom with `margin-top: auto`) — so all three read as one consistent card family, exactly like a typical SaaS homepage's product cards. It deliberately stays `card-flat` (no hover-lift) and its status line reads plain **"Launching soon"** with no arrow, mirroring `ModuleCard`'s own established no-href convention (`href` omitted → "Launching soon", no arrow; `href` present → "Explore →" / "Notify me →" with `ArrowRightIcon`). Don't add an arrow or hover-lift to the Bharat Agent card until `/agent` (or equivalent) actually exists as a route.
- **v5.4**: on explicit request ("too sober," referencing modern SaaS/marketplace homepages and the actual BharatNavya logo artwork for color), spread real brand color across more of the page instead of confining it to accents on white. A new `--navy`/`--navy-deep`/`--navy-mid`/`--navy-tint` token set was added, picked directly from the logo's lettering color — see Color palette below. This is a deliberate, requested exception to the "don't introduce a new hue" rule in What to avoid; `--navy` is scoped to **decorative surfaces only** (gradient panel backgrounds), never buttons/links/body text, so it doesn't reopen the v2 "navy read as basically black" problem — that verdict stands for interactive elements specifically. Concretely: (1) `.agent-hero-card`'s background moved from a pale, barely-there tint wash to a bold navy gradient (`--navy-mid` → `--navy` → `--navy-deep`) with orange/green radial glows in the corners — the white `.agent-hero-main`/`.agent-hero-product` cards now float on top of it, a light-cards-on-dark-panel treatment carried over from modern SaaS marketing pages generally, not copied from one specific site. (2) The final CTA card picked up the same navy-gradient-plus-glow treatment for bookend symmetry with the hero card, with its text flipped to white/`rgba(255,255,255,0.75)` and its primary button switched from `.btn-brand` to `.btn-primary` (orange reads better on navy than the blue-on-navy `.btn-brand` would). (3) The stats-strip numbers and the why-us pillar icon tiles now cycle through all four brand colors (`ACCENTS` array in `page.tsx`: brand → action → tricolor-green → navy, indexed by `i % ACCENTS.length`) instead of defaulting every instance to blue — cheap, low-risk color variety across sections that otherwise stayed white. (4) The Navbar (site-wide, not homepage-only) gained a 3px tri-color gradient hairline (`.nav-header::after`, navy → orange → green) replacing the plain grey `border-b`, and the logo badge's gradient changed from a hardcoded `#F97316→#EA580C` orange duotone to a token-driven `var(--navy)→var(--action)` gradient. Sections deliberately left untouched (advertise/how-it-works/feedback stayed white/light): per the frontend-design skill's restraint principle, the two bold navy panels (hero + final CTA) are the "spend your boldness here" moments — don't turn every section into a colored panel, that reads as busy rather than trendy.
- **v6 — Directory nav redesign**: on explicit request (referencing a two-row navbar pattern and a city+search combo pattern common on B2B/local-directory sites), the Directory's own navigation was reworked; **this scope is Directory-only** (`showDirectoryNav === true`) — the suite homepage/Navbar branch is untouched. See `components/Navbar.tsx`, `components/directory/CategoryStrip.tsx`, `lib/searchDock.tsx`, `components/home/HomeHero.tsx`, and the `.category-strip*`/`.search-city-*` rules in `globals.css`.
  1. **Row-1 simplified, category browsing moved to a persistent second row.** Directory's header row dropped `Products`/`Explore`/`Pricing`/`Blog` entirely (mobile and desktop) — it's now just Logo · [docked search when scrolled, desktop only] · search icon · +Sell · user menu. Category browsing lives in `CategoryStrip` (`components/directory/CategoryStrip.tsx`): a dark-navy (`--navy`) second row directly under the header — an "All Categories" trigger (reusing `CategoryMegaMenu`'s existing tree/flyout, just restyled for the dark strip and forced to the literal string "All Categories" rather than `t("nav.categories")`, since that key already resolved to the shorter "Categories" and would've silently won) followed by the first 7 root categories as plain inline links (`INLINE_COUNT`), pulled from the real `categories.json` tree via `useCategoryTree()` — not the reference site's raw-materials categories. Desktop only (`hidden nav:block`, ≥900px); mobile keeps the pre-existing `MobileCategoryAccordion` inside the hamburger menu.
  2. **Header + CategoryStrip are both sticky and stack together.** `.category-strip` is `position: sticky; top: 64px` (64px = the header's `h-16`) so it pins directly beneath the header rather than scrolling away — both stay visible together on scroll, not just the header.
  3. **The "All Categories" flyout must never live inside an `overflow-x:auto` container.** First attempt put the trigger inside the same flex row as the horizontally-scrollable inline category links, with `overflow-x:auto; overflow-y:visible` on that row — this *looked* right in the stylesheet but doesn't work: the CSS Overflow spec forces the computed value of `overflow-y` to `auto` any time `overflow-x` computes to non-visible on the **same box**, with no override, so the flyout was clipped to the row's 44px height regardless of the explicit `overflow-y: visible` declaration. Fix: `CategoryStrip` now renders `<CategoryMegaMenu />` as a sibling *outside* the scrollable region, with only the trailing inline links wrapped in their own `.category-strip-links` (which owns `overflow-x: auto` and never hosts a flyout). Same principle applies to any future dropdown/flyout that needs to sit next to a horizontally-scrollable strip: give the scrollable part its own nested container, don't share one element's overflow between "must scroll on one axis" and "must never clip on the other."
  4. **Scroll-docked search — docks into the main navbar itself, not a separate bar.** `HomeHero`'s hero search (Directory homepage only) is watched via `IntersectionObserver`; once it scrolls out of view, `lib/searchDock.tsx` (a small React context provided in `app/layout.tsx`, above `Navbar`) flips a shared `docked` flag that `Navbar.tsx` reads directly — Navbar renders a `size="compact"` `AISearchBar` inline in its own header row (desktop: inside the row's flex-1 slot next to the logo; mobile: as a second row still inside the same `<header>`, since mobile has no spare width to fold it into the h-16 row). This was an explicit redesign from an earlier version that docked a *separate* sticky bar below the header — the product owner wanted the search inside the main navbar, not a third floating row. Two things break this if you're not careful: (a) example chips (`showExamples`, default `true`) must be turned **off** for the desktop nav-embedded instance — the row is a fixed `h-16` flex row centered with `items-center`, so a taller child (search bar + wrapped chips) overflows both above *and* below the row rather than just growing it, visually spilling into CategoryStrip; the mobile instance keeps chips since it's its own block that's free to grow. (b) `HomeHero` must call `setDocked(false)` on unmount, or leaving the Directory homepage for another Directory page leaves the navbar stuck showing a dead search.
  5. **A city selector on `AISearchBar`** (`showCity` prop, opt-in — Consultations/`/search` don't set it): a native `<select>` (`.search-city-select`, per CLAUDE.md's native-`<select>`-for-filters rule) styled as a pill segment glued to the left of the input, using the existing `ALL_CITIES`/`PAN_INDIA_LABEL` from `lib/indiaGeo.ts` rather than a new list. No new filter plumbing — the selected city (if not "PAN India") is folded into the free-text query before calling `api.aiSearch()`, since the AI search already parses a location out of natural language.
  6. **Pre-existing, site-wide sticky-header bug fixed as a byproduct.** Verifying "does the header actually stay pinned on scroll" (via real CDP scroll + `getBoundingClientRect`, not just static screenshots) surfaced that the header was **not actually sticky anywhere in the app**, on any page — a regression baked in since v5.4. Two root causes, both cascade/spec traps rather than obvious typos: (a) `.nav-header { position: relative; }` (added in v5.4 purely so `::after` had a positioning context) has the exact same specificity as Tailwind's `.sticky` utility already on the header, and came later in the compiled stylesheet — it silently downgraded the header from `position: sticky` to `position: relative`. Removed; `position: sticky` is itself a valid positioned element, so the rule was redundant even before it became harmful. (b) `html, body { overflow-x: hidden }` (added for the CLAUDE.md zero-horizontal-overflow rule) hit the *same* implicit overflow-y-forcing spec behavior as (3) above, at the root level this time — changed to `overflow-x: clip`, which clips the same way without triggering the scroll-container/sticky-containing-block quirk. If you ever need `overflow-x` non-`visible` on an ancestor of anything `position: sticky`, reach for `clip` over `hidden` first and verify with a real scroll test, not just a static screenshot.
- **v7 — auth-CTA cleanup + hero card recolor**, both on explicit request.
  1. **One "Join us" affordance everywhere, no more Login+Register pairs.** The Navbar's guest-state Login+Register button pair (desktop actions row *and* the mobile menu's sticky footer) is gone — both now render a single `<Link href="/register">{t("nav.joinUs")}</Link>` (`btn-primary`), reusing the `nav.joinUs` key that already existed in `lib/i18n.tsx`. This **reverses the v5 "Auth-aware CTAs" note** that the Navbar's Login+Register pair was deliberately left alone — it's now unified with the rest of the site. `/login` itself is unchanged (still the two-tab OTP/password form) — it's simply no longer linked from the Navbar for a *new* visitor; its own "New to `{site}`? ‌Join us" link (`auth.createAccountLink` in `lib/i18n.tsx`, was "Create an account") still goes straight to `/register`, so wherever someone lands, "Join us" always means the same one-click path to registration. Apply this consistently: any future guest-facing entry point should offer a single "Join us" → `/register`, never a Login/Register pair.
  2. **The homepage intro CTA (above `AgentHeroCard`) only renders for logged-out visitors.** The "Go to dashboard" branch was removed outright (a logged-in visitor now sees nothing there, not a dashboard shortcut) — `{!loading && !user && <Link href="/register">Join us</Link>}`. Suite pages already don't expose Dashboard/My Listings/Inbox in the Navbar user menu (see Navigation patterns below); this keeps the homepage consistent with that — no dashboard entry point on suite-level pages, full stop, until a future request says otherwise.
  3. **The closing CTA card dropped both its dashboard button and its Directory-specific "Explore the Directory" button.** Reasoning: with more modules than Directory on the way, a closing section that only links to one of them reads as favoritism, not suite-wide messaging. Logged-out visitors still get a single "Join us" → `/register`; logged-in visitors now see **no button at all**, just the reassurance copy ("More modules are on the way — each one unlocks right here, under the same account, as it rolls out."). Copy for both states was also reworded to drop named-module references ("start sourcing from verified vendors", "start with the Directory today") in favor of generic "every module unlocks with the same login" language — don't reintroduce a single-module callout in this section without a fresh explicit request.
  4. **`AgentHeroCard`'s outer frame moved off the v5.4 bold dark-navy gradient to a light violet wash**, on explicit request referencing a lighter, more SaaS-typical AI-panel treatment — the near-black navy panel was a deliberate, flagged exception to begin with (see v5.4), and this walks it back toward the rest of the light design system rather than away from it. New tokens (`--violet-tint` `#f6f2fe`, `--violet-mid` `#eae0fc`, `--violet` `#d8c4f9`, `--violet-deep` `#b497f0`) were added to `:root`, following the exact same "decorative surfaces only, never buttons/links/body text" rule as `--navy` — see Color palette below. `.agent-hero-main` (the Bharat Agent card itself) now uses a *deeper* stop of the same violet family (`--violet-mid` → `--violet`) than the frame (`--violet-tint` → `--violet-mid`), so it still reads as the flagship against both the paler frame and the still-plain-white `.agent-hero-product` tiles beside it — this is the "background color of the Bharat Agent card should match the main card's color" request, read as "same family, one shade richer" rather than literally identical, since identical would make the card invisible against its own frame. Text inside `.agent-hero-main` stayed `--ink`/`--muted` (no color change needed — light-on-light, unlike the old white-on-navy scheme) except the status line, bumped from `--faint` to `--muted` for contrast against the new violet background. `.agent-hero-side-label` similarly flipped from a hardcoded `rgba(255,255,255,0.72)` (needed for the old dark frame) back to `var(--muted)` (the standard label color on light surfaces).
  5. **`.agent-hero-card` also got smaller and its body grid fluid**, fixing a "too much dead space on either side" complaint: `max-width` dropped from `1040px` to `900px`, and `.agent-hero-body`'s grid-template-columns changed from a fixed `minmax(0, 420px) minmax(220px, 260px)` (content capping out around 704px, centered inside a much wider card via `justify-content: center` — which left visible bare frame flanking the two inner cards) to a fluid `minmax(0, 1fr) minmax(220px, 280px)` with `justify-content` removed, so the main (Bharat Agent) column stretches to fill whatever width the card actually has. If `AgentHeroCard` is resized again, prefer fluid `fr` columns over a fixed px cap for the dominant column — a fixed cap re-opens the same dead-space problem at any card width wider than the cap.
- **v7.1** — item 4 above (the pale-lavender hero card) got explicit negative feedback ("purple color is not looking good") one turn later and was replaced, not tuned: **`--violet` went from a pale tint family to a dark, saturated one.** New values: `--violet-light: #8b5cf6`, `--violet: #6d28d9`, `--violet-deep: #3b0764`, `--violet-darker: #1e0442` (the old `--violet-tint`/`--violet-mid` names are gone, not just recolored — don't look for them). At this point *both* `.agent-hero-card` (the frame) and `.agent-hero-main` (the Bharat Agent card) used this dark violet gradient family — see v7.2 immediately below for why that was wrong.
- **v7.2** — one turn after v7.1, explicit feedback that the frame and the Bharat Agent card were now the *same* color and so read as one blob, not a card floating on a frame. Fix: **the two surfaces split apart instead of sharing the violet family.** `.agent-hero-card` (the frame) went back to plain white/`var(--canvas)`, with only a faint orange/green corner wash left (`rgba(245,130,31,0.14)` / `rgba(30,158,82,0.12)`, echoing the intro section's own restrained radial tint) and a normal `var(--border)` hairline — no more violet border, no more violet gradient on the frame. `.agent-hero-main` alone kept the dark violet gradient that used to be shared (`var(--violet) → var(--violet-deep) → var(--violet-darker)`, i.e. the *frame's* old v7.1 gradient, moved onto the card instead of the lighter `violet-light → violet` stop the card used in v7.1) and its border-color moved from `--violet-deep` to `--violet-darker` to match. `.agent-hero-side-label` flipped back to `var(--muted)` since it now sits on white again, not a dark frame. Net effect: Bharat Agent is now the one visibly colored, dark-violet flagship card sitting on a neutral white base, with Directory/Recruitment as plain white cards beside it — closer to how a single accent card would sit inside a plain container on a typical SaaS homepage. **Running lesson across v7/v7.1/v7.2**: don't let the frame and the "flagship" card inside it share one gradient family at similar depth — pick one surface to be the neutral base (originally violet-on-violet, now white) and let only the flagship element carry the bold color, or the two will visually merge exactly as reported here.
- **v8 (current) — category UI redesign**: explicit feedback that the "All Categories" mega-menu and the `/categories` full-directory listing both "look very normal" — asked for column/row borders, a UI pass, and background changes. Scope: `components/CategoryMegaMenu.tsx` (desktop flyout only — `MobileCategoryAccordion` untouched), `app/categories/page.tsx`, and the new `.megamenu-cell` rule in `globals.css`.
  1. **Mega-menu left rail is now a tinted nav rail, not a flat list on white.** `background: var(--bg-subtle)` on the rail `<ul>`; the active top-level item no longer just gets a `--brand-tint` background — it "pops" as a white (`var(--surface)`), bordered, `--shadow-card`-shadowed pill against the grey rail, a grey-rail/white-panel mega-menu convention common on large directory sites (grey nav rail, white content panel, raised selected state) rather than a flat tint-on-white highlight.
  2. **Mega-menu right panel's sub-category grid became a real bordered tile grid (`.megamenu-cell`).** Previously each sub-category was a bare text link floating in a `gap`-only grid — now each one (plus its own grandchildren, if any) sits inside a `var(--bg-subtle)`-filled, `var(--border)`-bordered, 10px-radius tile (`.megamenu-cell` in `globals.css`), hover state `var(--brand-tint)` fill / `#d3e2f7` border. This is the literal "add column/row border" ask — every cell has a visible border, so the grid reads as a grid. The header row above the grid (active category name + "View all in") also picked up a `border-bottom` + `padding-bottom` so it reads as a distinct row rather than floating text.
  3. **`/categories` page: each of the 24 top-level sections now carries a brand-accent identity, cycling the same 4-color rotation the homepage stats strip/why-us pillars use** (`ACCENTS` array, brand → action → tricolor-green → navy, `idx % ACCENTS.length` — the color carries no per-category meaning, it's purely visual rhythm across an otherwise-identical grid of 24 white cards). Concretely: a 3px `border-top` in the accent color, a tinted header band (`accent.tint` background behind the icon/name/count row, bleeding to the card's edges since the card's own padding moved from the `<section>` onto two inner wrapper `<div>`s), and the grandchildren pill chips recolored to `accent.tint`/`accent.border` instead of the flat `--bg-subtle`/`--border` every section shared before. A new pale border hex, `#dbe1ec` (navy tint's pale border), was added alongside the already-documented `#d3e2f7`/`#f9d9b8`/`#cdebd7` component-level pale borders for this — see Color palette.
  4. **`/categories` page: sub-category list rows got borders and a hover state, replacing a bare `gap`-only vertical stack.** Each `<li>` now has `border-top: 1px solid var(--border)` (skipped on the first row) plus `hover:bg-bg-subtle` — this is the "add row border" ask applied to the listing page specifically, distinct from item 2's tile-grid fix on the mega-menu. Don't confuse the two fixes: the mega-menu got a **tile grid** (bordered boxes with gaps), the `/categories` page got **bordered rows** (a bordered list, no gaps) — different content shapes called for different grid/list treatments, both satisfy "add borders" for their own layout.

## Brand principle for Bharat Agent

Bharat Agent is the flagship module but it is **not a rebrand of BharatSource** — same palette, same type, same components. As of v5 it's the page's hero card and deliberately the *dominant* element (Directory/Recruitment are nested inside it, smaller) — a reversal of v4's "equal weight, no dominant panel" stance, made on explicit request. It still earns distinction through its **orange module-identity color** and honest status copy ("In development") rather than invented capability claims. If a future request asks to de-emphasize it again, revert to the `ModuleCard`/`.home-modules-row` pattern kept as reference rather than inventing a third layout.

## Navigation patterns (Navbar)

`components/Navbar.tsx` has always branched on a `showDirectoryNav` boolean; v4 extended what that boolean controls and fixed a gap (`/recruitment` was falling into the Directory branch by omission — it's now in `SUITE_PATHS` alongside `/`, `/credit-card`, `/mutual`, `/consultations`, `/about`). When adding a new suite-level page (not part of the Directory product), add its path to `SUITE_PATHS`.

**v5 fix**: `SuiteProductsMenu`'s desktop trigger (`components/suite/SuiteNavMenu.tsx`) used to render with a bold `fontWeight: 500` override and a leading `BoxesIcon`, which made it look like a distinct button rather than a nav link sitting inline with `Blog`/`About us`. It now uses the exact same classes as the plain links (`text-sm text-muted hover:text-ink transition-colors`) plus just `inline-flex items-center gap-1` and a trailing chevron — no weight override, no leading icon. Any future nav dropdown trigger placed alongside plain text links should match their classes exactly rather than inventing its own weight/icon treatment, so the row reads as one consistent set of links.

- **Suite pages** (`showDirectoryNav === false`): nav shows `SuiteProductsMenu` (Directory + Recruitment dropdown) + Blog + About us. No Categories, Explore, Pricing, search, or +Sell.
- **Directory pages** (`showDirectoryNav === true`): **as of v6**, row-1 is minimal — Logo · [docked search when scrolled, see v6 in Version history] · search icon · +Sell · user menu. No `Products`/`Explore`/`Pricing`/`Blog` — category browsing lives in the persistent `CategoryStrip` second row (`components/directory/CategoryStrip.tsx`), which is sticky and stacks directly under the header. See v6 for the full breakdown (flyout-clipping trap, scroll-docking mechanics, city selector).
- **User dropdown/mobile footer is also gated by `showDirectoryNav`**: on suite pages, a logged-in user sees only their name/email + Logout. On Directory pages, the full menu (Dashboard, My Listings, Inbox, Admin-if-admin) returns. This is deliberate — Dashboard/Listings/Inbox are Directory-scoped concepts and don't belong on suite-level pages "for now" (product owner's words) — if a future module (e.g. Recruitment) gets its own dashboard tab, extend this gate rather than just re-enabling the Directory items on suite pages.
- **No language toggle in the Navbar** — `LanguageToggle` was removed from both the desktop actions row and the mobile overlay footer. The component and `lib/i18n` are untouched (still used for `t()` string lookups everywhere), just not exposed as a switcher in the nav.
- **Notifications are already always gated by `user &&`** in both desktop and mobile — no separate flag needed if you add a new nav icon that should only show when authenticated, follow that same `user && featureFlags.x && <Thing />` pattern.

## Auth-aware CTAs

Pattern used in the hero and closing CTA on `app/page.tsx`, via `useAuth()` (`{ user, loading }` from `@/lib/auth`):
- While `loading`, render nothing for the CTA (avoids a flash of the wrong state).
- Logged out: a single "Join us" button → `/register`.
- Logged in: **no button** — suite-level pages don't expose a dashboard entry point at all (v7; see Version history), so there's nothing to route a logged-in visitor to here. Show reassurance copy instead if the section needs one (see the closing-CTA copy in Version history v7.3).

**v7 update**: the Navbar's own guest-state actions (desktop actions row and the mobile menu footer) now follow this exact same single-"Join us"-button rule too — the old Login+Register pair is gone everywhere, not just on the homepage. Apply this one pattern (`loading` → nothing, `user` → no CTA or a dashboard-ish one only where a dashboard actually exists, else → single "Join us" → `/register`) to any new marketing CTA or nav affordance — don't show a signed-in visitor a "create account" button anywhere on the site, and don't reintroduce a separate Login/Register pair without a fresh explicit request.

## Page layout principles

- **One hero card, matched card family** (`AgentHeroCard`, v5.3 structure / v7–v7.2 color+sizing): Bharat Agent as its own `card card-flat` on the left (`.agent-hero-main`), Directory + Recruitment stacked as a compact vertical column of real `card` links on the right (`.agent-hero-side`) — `.agent-hero-body` is a fluid 2-column grid (`1fr` main column, v7), collapses to 1 column under 760px. The outer `.agent-hero-card` is a plain white/`--canvas` frame with a faint orange/green corner wash (v7.2 — it was briefly a matching dark-violet gradient in v7.1, and a pale-violet wash in v7, and a bold dark-navy gradient pre-v7), capped at `max-width: 900px` (v7, was `1040px`) and centered rather than stretching full-width. Bharat Agent is the dominant element by design (bigger card, more copy, and — as of v7.2 — the only colored surface in the group, a dark violet gradient against its white frame and its plain-white siblings) but shares the exact same icon/badge/copy/status-line structure as its siblings — see Version history and Brand principle above for why this replaced v4's three-equal-tiles row, v5.3 for why it's a real card rather than a mocked search bar, and v7–v7.2 for the full recolor journey and the fixed→fluid column fix.
- Every section lives in `.container-bs` and uses `.section-pad`/`.section-pad-sm`.
- Homepage section order: intro → module row → stats strip → advertise/brand-narrative (photo) → how-it-works (3 real steps) → client feedback (photo cards) → why-us (4 pillars) → closing CTA.
- Numbered step markers (`01`/`02`/`03`) only for a genuine ordered process (how-it-works).
- Don't repeat the same value prop in two sections.
- Section count: 4–6 is the default; the homepage's 8 was a deliberate, explicitly-requested exception for SaaS-homepage-like richness — don't keep adding sections without a specific reason.

## Animation / motion principles

One primitive: **`Reveal`** (650ms `cubic-bezier(0.16, 1, 0.3, 1)`, fires once via `IntersectionObserver`).

- **`direction` prop**: `"up"` (default), `"scale"`, `"left"`/`"right"`. The module row now uses plain `"up"` with a 0/80/160ms stagger for all three tiles (symmetric motion for a symmetric row) — reserve `"left"`/`"right"` for genuinely asymmetric "beside" layouts like the advertise section's photo/copy split.
- **Stagger, don't scatter**: 60–100ms increments per sibling group.
- **Signature motion is scoped**: `.chat-bubble`/`.typing-dot` CSS still exists in `globals.css` (for `BharatAgentPanel.tsx`'s reference shape) but isn't currently triggered by any live page, since the homepage no longer uses that component.
- **Hover affordance implies clickability** — only `.card` (has an `href`) gets lift-on-hover.
- `prefers-reduced-motion: reduce` handled once, globally.

## Hover / focus states

- Buttons: color shift + 0.5px `translateY` on `:active`.
- Interactive cards (`.card`): `translateY(-2px)` + `--shadow-card-hover` + `border-color: var(--border-strong)`.
- Focus: global `:focus-visible { outline: 2px solid var(--brand); }` — untouched, don't override per-component.

## Responsive behavior

- `.container-bs` max-width is fluid: `clamp(1200px, 92vw, 1600px)` — unchanged below ~1300px viewport, grows up to 1600px on wide monitors.
- Zero horizontal overflow at 390px is non-negotiable. Verified at 390/820/1440/1920px.
- Breakpoints in use: `860px` (`.home-modules-row` 3-col→1-col), `900px` (`.home-advertise-grid` 2-col→1-col).
- New layout classes belong in `globals.css` under a clearly commented section (`.home-modules-row`, `.home-advertise-grid`, `.home-feedback-grid`, `.home-eyebrow`) — named CSS classes, not ad-hoc Tailwind breakpoints, since inline `style` can't hold media queries.

## What to avoid

- Don't introduce a second font, a new hue outside brand/action/tricolor-green/navy/violet/status tokens, or a new shadow/radius value. (`--navy` was added in v5.4, `--violet` in v7, both explicitly requested — see Color palette. Neither reopens the door to arbitrary new hues.)
- Don't use `--navy` or `--violet` for buttons, links, or body text — decorative surfaces only (see the `--brand` row in Color palette for why).
- Don't reintroduce a Login+Register button pair anywhere (Navbar included) without a fresh explicit request — as of v7 every guest-facing entry point uses a single "Join us" → `/register` (see Auth-aware CTAs).
- Don't resurrect the v4 three-equal-tiles module row (`ModuleCard`/`.home-modules-row`) on the homepage without a new explicit request — v5's `AgentHeroCard` is current. Equally, don't push Bharat Agent back to equal-weight-with-siblings without a new explicit request either — see Version history.
- **Don't fabricate named individual testimonials with real-looking photos of specific people.** Feedback cards pair quotes with role+city attribution and a **local industry-context photo**, not a portrait claimed to be that reviewer.
- Don't overclaim a not-yet-live feature's current capability in copy (check tense/framing against actual product status).
- Don't pull Directory marketplace data into suite-level pages. The stats strip is explicitly **illustrative/dummy content**.
- **Never hot-link external/web images.**
- Don't show a logged-in user a "create account"/"sign in" CTA anywhere — use the auth-aware pattern above.
- Don't add Dashboard/My Listings/Inbox links to the user menu on suite pages — gate by `showDirectoryNav`, matching the rest of the Directory-scoped nav.
- Don't re-add the language toggle to the Navbar without an explicit request; `LanguageToggle.tsx`/`lib/i18n` still exist and work, they're just not surfaced in nav chrome right now.
- Don't add hover-lift to non-interactive elements, skip the Reveal wrapper on a section "because it's small," or add emoji/custom dropdowns in place of native `<select>`.
- Don't locally override `--brand`/`--action`/`--tricolor-green`/`.container-bs` per-page — they're token-level, site-wide by design.
- **Don't name specific competitor products/sites in code comments, docs, or user-facing copy** (explicit request — a prior pass scrubbed several such mentions from comments and one live feature description). Describe the *pattern* generically instead ("a two-row navbar with persistent category browsing," "a grey-rail/white-panel mega-menu") — the reasoning stays just as useful without the brand name.
